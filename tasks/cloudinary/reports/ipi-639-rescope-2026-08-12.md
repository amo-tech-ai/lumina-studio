## Decision — corrected per review (keep business separate)

**RESCOPE → CLOSE WITH PROOF for v1 provider moderation, but business approval remains separate:**

- **Provider moderation** (`moderation: manual` → `pending`/`approved`/`rejected` via Cloudinary Media Library) → `cloudinary_assets.moderation_status` + `asset_events` `kind: moderated` (provider, `reason: manual`, no `actorId`, `request_id` from Cloudinary) — **this PR's scope, proven above**
- **Business approval** (operator clicks Approve in iPix for `v1`) → **separate** `asset_approvals` or `asset_events` with `actorId` (who) + `reason` (comment) + `version` exact — **not in this docs rescope, deferred to IPI-639 proper or IPI-437 UI** — `insertAssetEvent` without `actorId` cannot satisfy `who/when/why/version` contract (`cloudinary-plan.md:98`)

**Why no `asset_approvals` for v1 provider moderation:** `moderation_status` + `asset_events` (`kind: moderated`) already gives exact-version provider audit with `request_id` composite idempotency and `is_org_member` RLS. `asset_approvals` with `actorId` is for **business** approval, not provider moderation — defer until business `approved ≠ published` gate is proven.

**4 hardenings applied in this branch (beyond 5-step proof):**
- `upsertCloudinaryAssetRecord` now `moderation_status: pending` on `isNewerVersion` overwrite for both provider-id and legacy public-id paths (approved v1 → v2 pending, not inherited)
- `handle_moderation_event` atomic via `public.handle_moderation_event` RPC:
  - `SELECT moderation_status, asset_id, version FROM cloudinary_assets WHERE cloudinary_asset_id=… AND version=… FOR UPDATE` — locks exact asset/version row
  - Same-status early return `unchanged` — prevents duplicate audit on retry
  - Real transition: `UPDATE moderation_status` + `INSERT asset_events kind=moderated` atomically in single function transaction
  - Uses Cloudinary `request_id` when present; when absent, generates `gen_random_uuid()` only after locked row confirms real transition (no UUID waste on same-status)
  - `ON CONFLICT (request_id, asset_id) WHERE request_id IS NOT NULL DO NOTHING` — composite idempotency, `23505` handled idempotently
  - Returns `changed`/`unchanged` to webhook — `unchanged` skips `ai_agent_logs` insert
  - Known limitation: UUID fallback intentionally prevents conflict dedup for notifications without Cloudinary request_id; same-status early return is primary dedup, but `approved→rejected→approved` same version without request_id creates distinct rows (different UUIDs). Upgrade path: persist stable provider delivery ID (`X-Cld-Notification-Id`) and use as `request_id`.
- `asset_events` for moderation is `kind: moderated` (provider, `reason: manual`) — business `approved` will be separate with `actorId`
- No stale `now()` — previous deterministic fallback `assetId:version:moderated:status` removed in favor of UUID-after-lock

## Why not `asset_approvals` for v1

- `moderation_status` (`pending/approved/rejected`) + `cloudinary_asset_id`+`version` + `asset_events` (`request_id` unique, `kind` moderated/approved/rejected) already gives exact-version audit, idempotency, and brand isolation
- `asset_approvals` would duplicate `moderation_status` without new business rule (e.g., `approved` ≠ `published` publish gate) — defer until such gate is proven required
- Reuse 95%: preset `ipix-signed-upload` + `sign-upload` `api_sign_request` + webhook `mapProviderIdentity` + `version` stale guard + `is_org_member` RLS
